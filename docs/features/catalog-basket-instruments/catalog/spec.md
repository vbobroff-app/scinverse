## 1. Зачем

Смысл наборов — **разными способами навыдергивать** из dump/Available только нужные
инструменты: на них обращаем внимание, за ними следим. В основном списке записи
**никогда** нет полного dump — только тормоза и вечный фильтр, ценности нет.

Раньше Online-каталог и hot-path были смешаны: в in-memory кэш попадал **весь** Online
слой (`active` — тысячи). Разделили:

- **широкий справочник** (Available — dump/Online в БД; виден при **формировании** наборов);
- **рабочий набор** (Observed — за чем **следим**: показываем и управляем; только он в кэше
  и в основном списке).

Расширить слежение — новый набор / правила; сузить — снять галку / Stop+Auto off.

---

## 2. Три слоя инструментов

| Слой | Имя в UI | Смысл | Где живёт |
|------|----------|--------|-----------|
| **Available** | (справочник / модалка наборов) | Все Online по lifecycle (`instrument.active = true`) | БД (+ ленивый UI), **не** hot-cache |
| **Observed** | Наблюдаемые | Union членов **отмеченных** ☑ baskets (`static` ∪ `dynamic` ∪ `system`) | БД (членство / правила) + **единственный** in-memory кэш записи |
| **Archive** | Архив | Просроченные (`active = false`) | БД; не Online-запись |

Ось lifecycle (exp → archive) **не меняется**. Observed — ортогональный working set поверх Available.

**Следим = один контур**, не три разных продукта:

- в **кэше** Host;
- в **основном списке** записи;
- **управляем** (Start / Stop / Auto) — только инструментами из Observed.

Снять галку набора → инструмент исчезает из списка и (если нет другой ☑-причины) из кэша.
Это **не** равно Stop записи само по себе: пока инструмент ещё в Observed (например через
☑ `Recording`), бэкенд продолжает писать / держать Auto. Суточный Lifecycle по-прежнему
проверяет актуальность по exp.

## 3. Basket (набор)

Пользовательские наборы — как списки в UI брокера. Системные — продукт добавляет **по
необходимости** (не закрытый enum навсегда).

```text
создать basket → имя (свободное) → kind → правила   # static | dynamic
system baskets → задаёт продукт, без модалки «создать»
```

Примеры имён UX (не зашиты): `CurrencyFutures`, `IndexFutures`, `OPT-Si`.

### 3.1 Типы (`kind`)

| Kind | Кто создаёт | Актуализация членства | Типичное содержимое |
|------|-------------|------------------------|-------------------|
| **`static`** | пользователь | Lifecycle / **Refresh**; материализация в БД | FUT (и явные OPT glob'ом) |
| **`dynamic`** | пользователь | Цена БА → окно ATM ±N; дописывает страйки в Observed из БД | OPT вокруг ATM |
| **`system`** | продукт | Live из состояния Host / покрытия; **набор system расширяем по мере нужды** | см. §3.4 |

В модели: `id`, `name`, `kind: static|dynamic|system`, `rules` (для static/dynamic), членство.
Имена пользовательских — только UX; у system — стабильный id (`recording`, `has_data`, …).

### 3.2 Правила (static) — T1 зафиксирован

- **Поле матча:** `short_name` — официальное **обозначение** контракта MOEX
  `XXXX-<месяц исполнения>.<год исполнения>` (напр. `Si-9.26`, `RTS-3.27`).
  Источник: TRANSAQ `<shortname>` / спека биржи («код (обозначение) Контракта»).
- **Не матчим** `ticker` / seccode (`SiU6`, `RIU6`) — краткий торговый код; для семейств
  по экспирации бесполезен. (`ticker` остаётся ключом `(ticker, board)` в модели.)
- **Fallback:** если `short_name` пуст (часто акции) — glob по `ticker`.
- **Синтаксис glob:** `*`, `?`, классы `[0-9]` / `[2-9]` и т.п.
- **Регистр:** case-insensitive; система нормализует.
- **Паттерны:** массив на basket, напр. `[RTS-*.2[0-9], SBRF-*.*, Si-*.*]` — в UI список,
  под капотом **OR**.
- **`sec_type` / board:** отдельные picker'ы рядом с glob (не пихать в паттерн) — см. §3.2.1.
- Матч: Available ∩ (glob OR-массив по `short_name`) ∩ picker → превью → OK.

### 3.2.1 Board (режим торгов)

**Board** — не «доска», а **режим торгов** на бирже: набор правил (расписание, способ торгов,
расчёты). Один тикер может торговаться на нескольких бордах; в модели инструмент
идентифицируется парой **`(ticker, board)`**.

В правиле static (`basket_rule.board_id`) — опциональный фильтр Available:

- задан → матч только инструменты этого борда;
- пусто / «Любой board» → без фильтра по борду.

| Код | Обычно значит |
|-----|----------------|
| **TQBR** | Фондовый рынок, основной режим T+ акции / ДР |
| **FUT** | Фьючерсы (срочный рынок / FORTS-контур в брокерских API) |
| **OPTS** | Опционы |
| **ROPD** | Отдельный режим (часто РЕПО / смежный контур в справочниках брокера; точное имя — в ISS/ASTS boards) |

**Стыковка с MOEX / ISS**

Иерархия справочника биржи: `engine → market → board → securities`.  
Полный список бордов рынка можно брать из ISS (`…/engines/{engine}/markets/{market}/boards`);
в Host уже есть `GetBoardsAsync` / API бордов (exchange catalog).

**As-is UI модалки:** picker board — **короткий stub** (`FUT` / `OPTS` / `ROPD` / `TQBR` +
«Любой»), не живой список из ISS. Подключение к exchange-catalog API — позже при нужде
(не блокирует канон фильтра `board_id`).

### 3.3 Правила (dynamic) — OPT

1. Страйки уже в Available/БД (dump / `get_option_families` → strikes → `get_options`).
2. Следим за **ценой БА** (FUT, обычно из static Observed).
3. В Observed/кэш **подкидываем** страйки ATM ±N (из БД).
4. **Выход из окна:** инструмент покидает dynamic-членство. Из Observed/кэша уходит **только
   если** нет другой ☑-причины остаться (типично — system `Recording`).  
   Чтобы больше не управлять OPT за пределами ±N: **Stop** и выключить **Auto** → нет
   `Recording` → вне окна → не в кэше.  
   Вернуть: снова попал в ATM **или** включить system-галку вроде `HasData` (см. ниже).

Окно dynamic — про состав слежения, не про принудительный Stop при движении last.

Параметры (TBD в реализации): ±N (default `Ohs:OptionAtmDepth`), ссылка на БА / parent FUT,
частота опроса цены. Политика Refresh dynamic — T3.

### 3.4 System (открытый список)

Пользователь **не** создаёт. В фильтре «Наборы» — стабильные строки, галки включают/выключают
вклад в Observed. Конкретный набор system **добавляем по необходимости**; первые кандидаты:

| Id (стабильный) | Default ☑ | Членство |
|-----------------|-----------|----------|
| **`recording`** | **вкл** | Кнопка записи **on** **или** Auto on — держит в кэше даже вне dynamic-окна |
| **`has_data`** | **выкл** | Есть **записанные сделки** (хоть тикнуло) **и** `active` (не expired). Auto on без тиков — **не** считается. Архив/`active=false` — вне набора |

Следующие system-id — по необходимости (T6); канон: kind = `system`, не зашивать «только два».

`recording` — **оверлей**, не третий отрезок рядом со static/dynamic: покрывает оба,
«не уже» множества «сейчас пишется / Auto».

```text
|---- static ----|---- dynamic ----|   ← правила «откуда набрали»
|=========== recording ===========|   ← system: запись on ∨ Auto (шире или равно)
```

`has_data` — оверлей (default ☐); предикат — T8 ниже. В фильтре галка есть и до v1.1, членство
включаем вместе с фичей.

**Пустой старт (v1):** без seed Si/RTS/SBRF — пользовательских baskets нет; ☑ `Recording` on.
В списке видны те, у кого запись/Auto (сейчас типично несколько инструментов на Auto).

**Scope baskets:** **per-connection** (у разных провайдеров разный dump/Available).  
Какой connection запускаем — тот у себя собирает dump; Observed-список и кэш — **не**
глобальный «весь active Host», а scope этой connection (сейчас часто один Finam, но
закладываем много коннекторов).  
**Галки наборов:** persist на **сервере** (не localStorage).

## 4. Суточный Lifecycle vs connect / crash

Наборы **собираются по правилам**. Снимок членства static в БД (`basket_member` и аналоги)
нужно **регулярно сверять** с Available:

- не остались ли **expired** (ушли в Archive / `active=false`) — выкинуть из членства;
- не появились ли в dump **новые**, подходящие под glob/picker — **добавить**.

Это как раз **суточный Lifecycle** и кнопка **Refresh** — не каждый connect и не каждый тик.
Dynamic — отдельный, более частый контур (**после v1**).

### 4.1 Утро / Lifecycle (и кнопка Refresh)

1. **Available** — сверить с источником (dump / invalidate): Online-список в БД;
   новые контракты месяца здесь; просроченные → Archive.
2. **Static baskets** — re-eval правил по Available → обновить членство в БД
   (снять expired, дописать новых матчей).
3. **Dynamic baskets** — (после v1) seed/сброс окна ATM; см. T2/T3.
4. **System** — live-предикаты (`recording` …) учитывать при сборке Observed.
5. **Кэш** — загрузить Observed = union **отмеченных** ☑ наборов.

Контракты обычно листятся заранее; mid-day сюрприз → оператор жмёт **Refresh**.

### 4.2 Когда что обновляем (static / v1)

| Событие | Available | `basket_member` (static) | Observed-кэш |
|---------|-----------|--------------------------|--------------|
| Суточный Lifecycle / **Refresh** | обновить + archive | **re-eval** всех static connection | пересобрать |
| OK в модалке (новые/правка правил) | — | eval этого basket | пересобрать, если ☑ |
| Обычный connect | dump может обновить БД | **нет** полного re-eval | мерж только текущий Observed |
| Галка набора ☑/☐ | — | — | пересобрать |
| Start / Stop / Auto | — | — | live `recording` |
| Crash / рестарт Host | — | читать снимок | поднять из БД + recording |

### 4.3 Connect / reconnect

Работаем **только с in-memory кэшем Observed** (мало инструментов).  
Полный dump при connect может обновить **Available в БД**; в кэш мержим **только** то, что
входит в Observed (без полного re-eval static на каждый connect после снимка).

### 4.4 Crash / рестарт Host

In-memory кэш слетает. **Не** гоняем static-правила заново без нужды:

1. Прочитать из БД снимок членства static (+ правила).
2. Поднять кэш Observed (с учётом текущих ☑ + live `recording`).
3. Dynamic (после v1): продолжить окно по цене БА; `recording` не даёт выпасть пишущимся.

Правила baskets — intent в БД; членство static — материализованный снимок до следующего
Lifecycle / Refresh / OK модалки.

## 5. UI

| Поверхность | Поведение |
|-------------|-----------|
| Основной список записи | Только **Observed**; здесь же **Start / Stop / Auto** (привилегия списка) |
| Фильтр «Наборы» | ☑ static/dynamic + ☑ system; пустой старт — только ☑ Recording |
| Фильтры 7d (recording / nonEmpty / selected / категории…) | **Оставляем** — режут уже **Observed** (кэш), не полный dump |
| Модалка baskets | Только **сформировать набор**. **Без** Start/Auto/тумблеров записи |
| Available | В модалке (колонка справочника), не в основном списке |

### 5.1 Фильтр «Наборы» (основной экран)

```text
Наборы
☑ SomeFutures      ← static (пользователь)
☑ ATM±15 OPT       ← dynamic (пользователь)
☑ Recording        ← system (всегда в списке галок)
☐ HasData          ← system, default выкл
```

### 5.2 Модалка набора — три колонки

Модалка = конструктор набора. Полный dump/Available — **здесь**. Управление записью —
**только** в основном списке Observed.

```text
┌─ Available ─────────┐  ┌─ Match (observed) ──┐  ┌─ Спецификация ─────────┐
│ dump / Online       │→│ превью членства     │  │ клик по инструменту    │
│ поиск / лениво      │ │ glob / ATM          │  │ карточка как у брокера  │
│ без кнопок записи   │ │ без Start/Auto      │  │ (read-only)            │
└─────────────────────┘  └─────────────────────┘  └────────────────────────┘
              создать / имя / kind / правила → OK
```

Static: match = Available ∩ glob (+ тип / underlying).  
Dynamic: match = превью окна ATM ±N по БА.  
OK сохраняет правила; галка набора на основном экране включает набор в Observed.

**Список в модалке** — свой UI: строки **без** кнопок и тумблеров записи.  
Клик по инструменту → **третья колонка: спецификация** (эталон — карточка Финам):

- заголовок: имя контракта + краткий код (напр. `Si-9.26` / `SiU6`);
- поля: категория, группа, тип поставки, экспирация, последний день обращения, лот, CFI
  и прочие атрибуты из Available/БД, что уже есть;
- без торговых действий и без Start/Auto.

Точный набор полей и live-котировки (bid/ask) в модалке — TBD (T7); канон: спека видна,
управление записью — нет.

## 6. Связь с Refresh / Lifecycle

Канон действий вынесен в [`../life-cycle/spec.md`](../life-cycle/spec.md). Кратко:

- Refresh = invalidate dump + сброс OPT + **force** sweep;
- sweep = archive → re-eval static → rebuild Observed (dynamic — после v1);
- гейт «раз в checkup-сутки» — только БД (`ohs_runtime_state`), не память Host
  ([life-cycle §2.1](../life-cycle/spec.md));
- NC: сутки → **Lifecycle**; Refresh → **Action** + **Checkup**
  (ось: периодичность / разовая health-проверка — [`nc/threads`](../../nc/threads/spec.md)).
